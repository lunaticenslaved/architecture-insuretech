# Анализ проблем и рисков текущей архитектуры InsureTech

## Проблемы производительности и масштабируемости

1. Синхронная цепочка `Web → core-app → ins-product-aggregator → N страховых компаний` — время ответа определяется самым медленным API. При добавлении новых страховых деградация нарастает линейно.
2. Риск таймаутов и нарушения SLA при медленных ответах от страховых компаний.
3. Сбой одной страховой компании влияет на весь агрегированный ответ.
4. Один B2B-партнёр может отправить 250 RPS при лимите 20 RPS и исчерпать ресурсы всего `core-app` — нет rate limiting.
5. B2B и B2C трафик не изолированы, прямой доступ через LoadBalancer без API Gateway.
6. `core-app` — монолит: поиск (50 RPS) и оформление (10 RPS) конкурируют за одни ресурсы.

## Проблемы данных и консистентности

1. Единственный экземпляр PostgreSQL для всех сервисов — единая точка отказа и узкое место.
2. Тарифы запрашиваются синхронно при каждом поиске — нет кэширования.
3. Нет гарантированной доставки данных об оформленных страховках в `ins-comp-settlement`.
4. Ежемесячная синхронная выгрузка реестров — риск потери данных при сбоях.

## Операционные риски

1. Нет мониторинга и алертинга — команда узнаёт об инцидентах от пользователей (500 тыс. руб./час простоя).
2. Одна зона доступности — отказ ноды или зоны означает полный простой.
3. PostgreSQL без репликации и failover — любой сбой БД роняет продукт.
4. Нет circuit breaker при вызовах внешних API — каскадные сбои.
5. Нет HPA и нагрузочного тестирования перед ожидаемым ростом трафика.

---

## Предлагаемое решение (быстрый фикс)

**Цель:** подключить ещё 5 страховых компаний без деградации производительности, с минимальными изменениями архитектуры.

### 1. Асинхронное кэширование тарифов через Kafka

`ins-product-aggregator` опрашивает страховые компании в фоне и публикует тарифы в Kafka. `core-app` консьюмит события и хранит тарифы в локальном кэше.

- Поисковые запросы обслуживаются из кэша — синхронный вызов `core-app → ins-product-aggregator` с критического пути убирается
- Добавление новых страховых компаний не влияет на время ответа пользователю
- API сервисов не меняются

### 2. Асинхронная доставка событий оформления (Transactional Outbox)

При оформлении страховки `core-app` в **одной транзакции** записывает данные полиса и событие в таблицу `outbox` в `core-db`. Отдельный **Message Relay** читает из `outbox` и публикует в Kafka. `ins-comp-settlement` консьюмит события идемпотентно.

```
core-app DB Transaction:
  INSERT INTO policies ...   -- данные страховки
  INSERT INTO outbox ...     -- событие оформления
  COMMIT

Message Relay → Kafka → ins-comp-settlement (idempotent)
```

**Гарантии:** событие не теряется при недоступности Kafka (остаётся в `outbox`); дубликаты отбрасываются идемпотентным консьюмером.

### 3. Разнесение БД на отдельные ВМ

Базы данных каждого сервиса (`core-db`, `ins-comp-settlement-db`, `client-info-db`) выносятся на отдельные ВМ — изоляция нагрузки и устранение SPOF.

### Итог

| | До | После |
|---|---|---|
| Время ответа на поиск | Зависит от N внешних API | Из кэша, константное |
| +5 страховых компаний | Деградация производительности | Без влияния на latency |
| Потеря финансовых событий | Возможна при сбоях | Исключена (Outbox + Kafka) |
| SPOF базы данных | Единый PostgreSQL | Изолированные БД на отдельных ВМ |
