# Архитектура нового продукта: ОСАГО онлайн

### Контекст и ограничения

- Предложения от страховых отображаются **по мере поступления**, не ожидая остальных
- Страховые предоставляют polling API: `POST /osago/request` + `GET /osago/request/{id}`
- Максимальное ожидание ответа от страховой — **60 секунд**
- Пиковая нагрузка — **2 500 одновременных пользователей**

---

### 1. Нужна ли osago-aggregator своя БД?

**Да.** Агрегатор создаёт заявки во всех страховых и циклически опрашивает их до получения результата. Для этого нужно хранить:
- соответствие ID заявки InsureTech → ID заявок в каждой страховой компании
- статус опроса по каждой страховой
- полученные предложения

Без хранилища рестарт сервиса приведёт к потере всех незавершённых заявок.

**Хранилище:** `osago-aggregator-db` — PostgreSQL на отдельной ВМ.

---

### 2. Интеграция core-app ↔ osago-aggregator

**Kafka** (async), по аналогии с подходом для тарифов:

- `core-app` публикует заявку в топик `osago-requests`
- `osago-aggregator` консьюмит, создаёт заявки в страховых, опрашивает результаты
- Каждое полученное предложение **немедленно** публикуется в топик `osago-offers`
- `core-app` консьюмит и сразу доставляет предложение на фронтенд

Синхронный REST между сервисами не подходит: процесс опроса страховых занимает до 60 сек, что привело бы к удержанию соединений и деградации core-app.

**Контракт событий:**
- Топик `osago-requests`: `{ requestId, clientData, vehicleData }`
- Топик `osago-offers`: `{ requestId, insurerId, offer, status }`

---

### 3. API веб-приложения в core-app

REST-polling с фронтенда неэффективен при 2 500 пользователях (каждый делал бы повторные запросы). Используется **SSE (Server-Sent Events)**:

- `POST /api/osago/requests` — создать заявку, вернуть `requestId`
- `GET /api/osago/requests/{requestId}/offers` — SSE-стрим: core-app пушит каждое новое предложение из Kafka клиенту в реальном времени

SSE выбран вместо WebSocket, т.к. данные идут только в одну сторону (сервер → клиент); он проще в реализации и работает через стандартный HTTP без специального прокси.

---

### 4. Паттерны отказоустойчивости

```
Web ──SSE──► core-app ──Kafka──► osago-aggregator ──polling──► Страховые компании
```

| Участок | Паттерн | Обоснование |
|---|---|---|
| osago-aggregator → страховая | **Timeout 60s** | Бизнес-требование: не ждать дольше |
| osago-aggregator → страховая | **Retry с backoff** | Повтор при транзиентных сбоях в рамках 60 сек |
| osago-aggregator → страховая | **Circuit Breaker** | Если страховая стабильно не отвечает — прекратить опрос, не занимать потоки |

---

### 5. Поток данных

```
1. Пользователь → POST /api/osago/requests
2. core-app → Kafka [osago-requests]
3. osago-aggregator: создаёт заявки в N страховых (параллельно)
4. osago-aggregator: polling каждые X сек (Timeout 60s, Retry, Circuit Breaker)
5. Получен ответ от страховой → Kafka [osago-offers]
6. core-app консьюмит → пушит в SSE-стрим
7. Предложение появляется на экране пользователя
```

---

### 6. Масштабирование при 2 500 пользователях

- **osago-aggregator**: HPA, горизонтальное масштабирование по Kafka-партициям. 10 страховых × 2 500 пользователей = 25 000 параллельных polling-сессий → обязателен неблокирующий I/O (корутины / reactive).
- **core-app**: 2 500 долгоживущих SSE-соединений → async-сервер (Spring WebFlux / Ktor). HPA по CPU/RPS.

---

### 7. Применение паттерна Transactional Outbox

В архитектуре ОСАГО есть две точки, где сервис должен одновременно обновить БД и опубликовать событие в Kafka. Сбой между этими операциями приведёт к потере данных. Для обеих точек применяется **Transactional Outbox**.

#### Точка 1: core-app при создании заявки

`core-app` должен сохранить заявку в `core-db` и опубликовать событие в топик `osago-requests`.

**Риск:** заявка сохранена, но Kafka недоступна — `osago-aggregator` не получит заявку, пользователь не увидит предложений.

```
core-app DB Transaction:
  INSERT INTO osago_requests ...   -- сохранить заявку
  INSERT INTO outbox ...           -- событие для osago-aggregator
  COMMIT

Message Relay → читает outbox → публикует в Kafka [osago-requests]
```

#### Точка 2: osago-aggregator при получении предложения от страховой

`osago-aggregator` должен обновить статус заявки в `osago-aggregator-db` и опубликовать предложение в топик `osago-offers`.

**Риск:** предложение сохранено в БД, но Kafka недоступна — `core-app` не узнает о нём, предложение не дойдёт до пользователя.

```
osago-aggregator DB Transaction:
  UPDATE osago_requests SET status = 'offer_received' ...
  INSERT INTO outbox ...   -- предложение от страховой
  COMMIT

Message Relay → читает outbox → публикует в Kafka [osago-offers]
```

#### Где применяется

| Сервис | Событие | Топик | Риск без Outbox |
|---|---|---|---|
| `core-app` | Создание ОСАГО-заявки | `osago-requests` | Заявка не дойдёт до osago-aggregator |
| `osago-aggregator` | Предложение от страховой | `osago-offers` | Предложение не дойдёт до пользователя |

Паттерн гарантирует: либо и БД обновлена, и событие опубликовано — либо ничего. Дубликаты при повторной доставке отбрасываются идемпотентными консьюмерами на стороне получателя.
